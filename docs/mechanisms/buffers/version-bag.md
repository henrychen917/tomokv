# `tomoVerMeta` — per-version metadata and the version bag

## What the mechanism is

A version “bag” is not a separately allocated array or container. It is a chain of `kvobj`/`redisObject` allocations: every versioned object points to one separately allocated `tomoVerMeta`, and the keyspace table points at the newest physical object. Ordinary object constructors initialize `vmeta = NULL`; metadata is allocated lazily by the versioned-write path. ([`src/object.c:62-118`](../../../src/object.c#L62-L118), [`src/object.c:185-196`](../../../src/object.c#L185-L196), [`src/db.c:469-501`](../../../src/db.c#L469-L501))

The metadata gives the same objects two views:

- `version_prev` is the physical, newest-install-first chain. A versioned overwrite publishes the new object as the table head with the old head as `version_prev`; it may inspect the predecessor metadata to inherit `committed_head` and mark that predecessor `SUPERSEDED`, but it does not traverse, reorder, retire, or rewrite the existing `version_prev` link chain. ([`src/db.c:476-494`](../../../src/db.c#L476-L494), [`src/db.c:856-861`](../../../src/db.c#L856-L861), [`src/db.c:904-910`](../../../src/db.c#L904-L910))
- `committed_head` is the per-key cursor to the newest committed candidate, and `committed_prev` links committed candidates in descending order. The actual insertion comparison is descending `(version_seq, version_order)`: a new node precedes the cursor when `new_seq > old_seq || (new_seq == old_seq && new_version_order > old_version_order)`. The nearby comment says `(seq,install_order)`, but the executable tie-breaker is `version_order`. ([`src/db.c:967-1009`](../../../src/db.c#L967-L1009))

The physical chain may end in an old raw object with no metadata. The committed walk treats that raw tail as sequence zero and returns it when no newer eligible metadata node is found. ([`src/db.c:977-994`](../../../src/db.c#L977-L994), [`src/server.c:10243-10256`](../../../src/server.c#L10243-L10256))

Two source assertions constrain byte packing rather than total size: `single_state` is exactly two bytes after `detached`, and `owner_ops_pending` occupies the next four-byte-aligned position after `single_state`. ([`src/object.h:169-178`](../../../src/object.h#L169-L178))

On an ABI with 8-byte pointers and `uint64_t`, 4-byte `unsigned int` and enum, and ordinary natural alignment, the declaration derives to 144 bytes: the scalar/flag prefix through `owner_ops_pending` occupies 52 bytes, four padding bytes precede five pointers at offsets 56–95, and two 24-byte `tomoOwnerOp` records occupy offsets 96–143. This 144-byte value is ABI-derived; the source has no `sizeof(tomoVerMeta)` assertion. ([`src/object.h:105-115`](../../../src/object.h#L105-L115), [`src/object.h:136-178`](../../../src/object.h#L136-L178))

There is no explicit cache-line alignment or padding on `tomoVerMeta`; `zcalloc(sizeof(*vmeta))` creates one allocation per metadata record. Unless `CACHE_LINE_SIZE` is externally predefined, the source selects 64 bytes normally and 128 bytes on Apple AArch64. A 144-byte LP64 record contains 2.25 64-byte cache-line equivalents or 1.125 128-byte equivalents, necessarily touching at least three or two lines respectively and possibly one more depending on allocation placement. The associated `redisObject`/`kvobj` allocation and any storage it owns are additional to this metadata, so `N` metadata-bearing versions require `N * sizeof(tomoVerMeta)` metadata bytes plus those object allocations and allocator overhead. ([`src/config.h:38-44`](../../../src/config.h#L38-L44), [`src/db.c:469-472`](../../../src/db.c#L469-L472), [`src/object.h:182-197`](../../../src/object.h#L182-L197))

The chain has no fixed capacity, mask, or growth allocation: each install adds one object and one metadata allocation, while pruning removes eligible linked objects. ([`src/db.c:469-501`](../../../src/db.c#L469-L501), [`src/db.c:761-763`](../../../src/db.c#L761-L763), [`src/db.c:1208-1243`](../../../src/db.c#L1208-L1243))

## Publication and memory ordering

| Publication | Producer operation | Consumer operation and guarantee |
| --- | --- | --- |
| Attach metadata to an object | `kvobjSetVmeta` release-stores `kv->vmeta`. | `kvobjVmeta` acquire-loads it, making the initialized metadata visible. ([`src/object.h:219-225`](../../../src/object.h#L219-L225)) |
| Physical and committed links | Link setters use release stores. | Link getters use acquire loads. Initial `version_prev` is a plain pre-publication initialization. ([`src/object.h:237-255`](../../../src/object.h#L237-L255), [`src/db.c:493-500`](../../../src/db.c#L493-L500)) |
| Commit an attached/live version | The owner release-stores its final `version_seq`, then release-publishes it through either a predecessor's `committed_prev` or the physical head's `committed_head`; a detached version is stamped but intentionally skips cursor publication. | Readers of the live bag acquire-load `committed_head`, every metadata pointer, `version_seq`, and `committed_prev`. ([`src/db.c:944-1009`](../../../src/db.c#L944-L1009), [`src/server.c:10242-10254`](../../../src/server.c#L10242-L10254)) |
| Cancel decision | Completion release-stores `version_canceled`. | The own-uncommitted scan acquire-loads it before considering origin identity. ([`src/server.c:10320-10323`](../../../src/server.c#L10320-L10323), [`src/server.c:10137-10146`](../../../src/server.c#L10137-L10146)) |
| Fast-path license | A successor release-stores `SUPERSEDED`; an owner prune may release-store `COMMITTED`. | `kvobjSingleCommitted` acquire-loads the state before the read fast path uses it. ([`src/db.c:477-489`](../../../src/db.c#L477-L489), [`src/db.c:1051-1086`](../../../src/db.c#L1051-L1086), [`src/object.h:227-230`](../../../src/object.h#L227-L230)) |
| Owner operation | Completion fills an embedded `owner_op`, then `csStampPush` release-stores the owner lane's queue tail. | The owner queue pop observes the released tail, decodes the record, and performs stamp/cancel/prune while holding that key owner's worker lock. ([`src/server.c:10320-10328`](../../../src/server.c#L10320-L10328), [`src/server.c:10060-10086`](../../../src/server.c#L10060-L10086), [`src/server.c:9987-10041`](../../../src/server.c#L9987-L10041)) |
| Pending-operation count | Completion release-stores `1` for cancel or `2` for stamp plus prune; the owner decrements with `memory_order_acq_rel`. | Retirement and fast-license checks acquire-load zero before unlinking or licensing. ([`src/server.c:10320-10328`](../../../src/server.c#L10320-L10328), [`src/server.c:10006-10035`](../../../src/server.c#L10006-L10035), [`src/db.c:1059-1078`](../../../src/db.c#L1059-L1078)) |

The owner-operation transport is the reserved lane `server.io_threads + server.tm_ngrow_io` of each worker's `exQueue` matrix. Successive operations may originate on different completion workers, but `commit_lock` serializes their pushes, so `exQueuePushOwnerOp` treats them as one logical SPSC producer. The drain still specifies no stamp arrival order and drains to empty; correctness therefore comes from sorted committed-chain insertion rather than queue arrival order. ([`src/server.c:9979-9995`](../../../src/server.c#L9979-L9995), [`src/server.c:10290-10334`](../../../src/server.c#L10290-L10334), [`src/server.c:10349-10403`](../../../src/server.c#L10349-L10403), [`src/server.c:20972-20984`](../../../src/server.c#L20972-L20984), [`src/db.c:971-994`](../../../src/db.c#L971-L994))

`worker->stamp_pending` is release-incremented after a push and acquire-tested both by the owner drain and by the read relevance gate; the owner release-decrements it only after processing the batch. It is a relevance/count signal, while the queue's tail publication is the record-transfer edge. ([`src/server.c:9987-9989`](../../../src/server.c#L9987-L9989), [`src/server.c:10047-10056`](../../../src/server.c#L10047-L10056), [`src/server.c:10060-10086`](../../../src/server.c#L10060-L10086), [`src/server.c:10227-10236`](../../../src/server.c#L10227-L10236))

## Step-by-step algorithm

### 1. Install a physical version

1. `setKeyVersioned` selects add or overwrite through `setKeyByLinkVersion`; versioned MSET-style callers pass `TOMO_VERSION_UNCOMMITTED` in the group field. ([`src/db.c:1569-1572`](../../../src/db.c#L1569-L1572), [`src/db.c:1583-1627`](../../../src/db.c#L1583-L1627), [`src/server.c:9919`](../../../src/server.c#L9919))
2. `tomoVerMetaNew` zero-allocates metadata, relaxed-initializes `version_seq`, `single_state = NONE`, and `version_canceled = 0`, selects `PENDING` for `UINT64_MAX` or `APPLIED` otherwise, sets retirement `ACTIVE`, and records the physical predecessor/store/database. ([`src/db.c:469-501`](../../../src/db.c#L469-L501))
3. If a predecessor has metadata, the new head acquire-inherits its `committed_head` cursor and release-marks that predecessor `SUPERSEDED`; otherwise it inherits the raw predecessor itself. The new metadata then release-stores that inherited cursor. ([`src/db.c:476-494`](../../../src/db.c#L476-L494))
4. The new object release-attaches its metadata and becomes the keyspace head; on the FLAT versioned branch the old object is retained as the untouched `version_prev` chain. ([`src/object.h:223-225`](../../../src/object.h#L223-L225), [`src/db.c:856-861`](../../../src/db.c#L856-L861), [`src/db.c:904-910`](../../../src/db.c#L904-L910))
5. `csMsetRecordInstall` assigns a relaxed group-array index, stores `install_order = base + index`, the real client's ID, `version_order = index`, owner, and lifecycle identity, and retains the installed object in `g->mset_installs[index]`. ([`src/server.c:11432-11451`](../../../src/server.c#L11432-L11451), [`src/server.c:367-384`](../../../src/server.c#L367-L384))

### 2. Decide, stamp, and publish a group

1. In the real client's completion order, `csMsetStampAndAppend` cancels for `version_abort` or any `MSETNX` `PRESENT` position; otherwise it assigns `seq = fetch_add(next_seq, 1, relaxed) + 1`. ([`src/server.c:10290-10311`](../../../src/server.c#L10290-L10311))
2. For every recorded install, it release-stores the cancel bit and pending-operation count. A canceled version receives one `{kv, 0, CANCEL}` record; a successful version receives `{kv, seq, STAMP}` and `{kv, seq, PRUNE}`, with the stamp pushed immediately. ([`src/server.c:10312-10329`](../../../src/server.c#L10312-L10329))
3. The commit drain release-stores `commit_seq = group.version_seq` only for a successful group and only after every stamp push; it then pushes every prune record. A canceled group publishes no sequence and has already queued all cancels. ([`src/server.c:10363-10389`](../../../src/server.c#L10363-L10389))
4. The owner drain consumes under the worker lock. `STAMP` calls `tomoApplyVersionStamp` before changing pending operations from 2 to 1; `PRUNE` decrements 1 to 0 before calling `tomoArmVersionRetire`; `CANCEL` decrements 1 to 0 before calling `tomoCancelVersion`. ([`src/server.c:9997-10040`](../../../src/server.c#L9997-L10040))
5. Stamping release-stores the final sequence, sets `APPLIED`, and clears reservations for both attached and detached versions. For an attached/live bag it also searches the committed chain with the exact descending comparison above, release-links the new predecessor, and advances either the prior committed link or the head cursor; older arrivals insert in history without moving the maximum backward. A detached version deliberately skips live-head lookup and cursor publication. ([`src/db.c:944-1010`](../../../src/db.c#L944-L1010))
6. Cancellation leaves `version_seq == UINT64_MAX`, changes the plain owner-controlled state to `CANCELED`, clears reservations, and either schedules a detached node for physical retirement or changes a live node from `ACTIVE` to `PRUNE_GRACE` and queues version-prune retirement. ([`src/db.c:1024-1049`](../../../src/db.c#L1024-L1049))

### 3. Resolve a read

1. `lookupKeyReadWithFlags` returns the raw head unchanged when it has no metadata. With metadata and atomic mode enabled, it first tries the `SINGLE_COMMITTED` path and accepts that head when no pinned snapshot excludes its acquired sequence; every other metadata path calls `kvobjVersionAt` with the pinned or current read snapshot and current client. ([`src/db.c:361-397`](../../../src/db.c#L361-L397))
2. `kvobjVersionAt` maps a fake reader to its real parent. In a worker context it can skip the physical own scan only when that real client's acquire-loaded `mset_pending_count` is zero and that worker's acquire-loaded `stamp_pending` is also zero; a non-worker resolve context retains the scan. ([`src/server.c:10206-10236`](../../../src/server.c#L10206-L10236))
3. When needed, the own scan walks `version_prev` newest first. It accepts only `version_seq == UINT64_MAX`, `version_canceled == 0`, and matching immutable `origin_client_id`; a matching tombstone returns absence. ([`src/server.c:10133-10148`](../../../src/server.c#L10133-L10148))
4. Otherwise the resolver acquire-loads `committed_head` and walks `committed_prev`. It stops at the first metadata version satisfying `seq <= snapshot` or matching the reader's real-client ID; a selected tombstone returns absence. A `NULL` reader has ID zero and therefore gets only the strict committed-snapshot branch. ([`src/server.c:10242-10256`](../../../src/server.c#L10242-L10256))

### 4. Prune and collapse the bag

1. A successful prune operation requires an applied matching sequence no greater than the global committed frontier and zero pending owner operations. A live `ACTIVE` node becomes `PRUNE_GRACE` and queues a version-prune grace callback; a detached active node can go directly to physical retirement. ([`src/db.c:1089-1105`](../../../src/db.c#L1089-L1105))
2. The owner may publish `SINGLE_COMMITTED` only when the candidate is attached, non-tombstone, applied, still `NONE`, has zero pending owner operations, is both `committed_head` and has no `committed_prev`, and every physical predecessor is a fully canceled zero-pending metadata node. ([`src/db.c:1051-1086`](../../../src/db.c#L1051-L1086))
3. After the first grace, pruning re-enters a sequentially consistent FLAT section, waits out resize, and takes the owner lock before inspecting or changing the live bag. ([`src/db.c:1134-1164`](../../../src/db.c#L1134-L1164))
4. A canceled metadata node is eligible under either anchor exactly when `retire_state == TOMO_RETIRE_ACTIVE` and an acquire load finds `owner_ops_pending == 0`. For a non-canceled node, a canceled anchor admits nothing; a committed anchor starts with `eligible = seq < retire_max`, then excludes metadata that is uncommitted, newer than the visible global frontier, not `APPLIED`, or still has an owner operation. ([`src/db.c:1187-1231`](../../../src/db.c#L1187-L1231))
5. Eligible physical nodes are unlinked without reordering survivors and enter physical retirement. For a non-cancel anchor, a second pass stably filters `PHYSICAL` nodes from the already sorted committed chain and release-publishes the repaired cursor. ([`src/db.c:1233-1268`](../../../src/db.c#L1233-L1268), [`src/db.c:1284-1289`](../../../src/db.c#L1284-L1289))
6. If no physical node survives, pruning deletes the key through `dbSyncDelete` immediately. Otherwise it counts non-canceled committed and uncommitted survivors; a raw tail counts as committed and ends the scan. ([`src/db.c:1269-1289`](../../../src/db.c#L1269-L1289), [`src/db.c:1322-1343`](../../../src/db.c#L1322-L1343))
7. Tombstone deletion requires `committed == 1`, `uncommitted == 0`, a non-NULL `sole_committed`, metadata on that node, `version_tombstone != 0`, and one of: `sole_committed == anchor`, `retire_state == TOMO_RETIRE_ACTIVE`, or `retire_state == TOMO_RETIRE_PRUNE_GRACE && !lifecycle_ref_held`. Only then does it call `dbSyncDelete`. ([`src/db.c:1345-1373`](../../../src/db.c#L1345-L1373))
8. Raw-head promotion requires `committed == 1`, `uncommitted == 0`, a non-NULL `sole_committed`, `version_prev == NULL`, metadata on that node, `version_tombstone == 0`, and either `sole_committed == anchor` or `!lifecycle_ref_held`; the branch asserts `stamp_state == TOMO_STAMP_APPLIED` and acquire-loads `owner_ops_pending == 0`, release-points `committed_head` at the sole value, release-detaches `vmeta`, and retires that metadata through QSBR. ([`src/db.c:1375-1400`](../../../src/db.c#L1375-L1400))

A non-versioned overwrite or delete detaches the entire physical bag: it marks every metadata node `detached`, immediately schedules only terminal zero-pending nodes for physical retirement, and leaves uncommitted nodes protected until their queued owner operations run. ([`src/db.c:1108-1132`](../../../src/db.c#L1108-L1132))

## Invariants enforced by the code

- A version installed for an atomic group starts at `version_seq == TOMO_VERSION_UNCOMMITTED`; only an owner `STAMP` replaces it with a nonzero finite sequence, while a canceled group node remains uncommitted forever. `tomoVerMetaNew` also accepts a finite initial sequence and initializes that separate case as `TOMO_STAMP_APPLIED`. ([`src/object.h:180`](../../../src/object.h#L180), [`src/db.c:469-501`](../../../src/db.c#L469-L501), [`src/db.c:944-949`](../../../src/db.c#L944-L949), [`src/db.c:1028-1035`](../../../src/db.c#L1028-L1035))
- Physical order is install order and does not define or necessarily match visibility order; committed visibility comes from the separately sorted cursor chain. ([`src/db.c:904-910`](../../../src/db.c#L904-L910), [`src/db.c:971-1009`](../../../src/db.c#L971-L1009))
- A metadata-bearing node cannot enter physical retirement until it is stamped or canceled and `owner_ops_pending == 0`; repeated scheduling is idempotent once `retire_state == PHYSICAL`. A raw physical tail has no stamp/cancel state and follows the raw retirement branch. ([`src/db.c:927-942`](../../../src/db.c#L927-L942))
- The immutable real-client `origin_client_id` survives stamping; both an uncommitted own scan and a committed own-widening test use it, while other readers still obey their snapshot. ([`src/object.h:139-143`](../../../src/object.h#L139-L143), [`src/db.c:1011-1021`](../../../src/db.c#L1011-L1021), [`src/server.c:10137-10146`](../../../src/server.c#L10137-L10146), [`src/server.c:10242-10255`](../../../src/server.c#L10242-L10255))
- `SUPERSEDED` is published before a successor head and is never converted back to a fast-path license; only a `NONE` head can become `COMMITTED`. ([`src/db.c:477-489`](../../../src/db.c#L477-L489), [`src/db.c:1059-1086`](../../../src/db.c#L1059-L1086))
- The install's owner/bucket lifecycle reference is acquired before the version can retire. It is normally released after owner-affine work and the armed prune callback; if resize or teardown suppresses that callback, `flatRetirePayloadDiscard` releases the reference directly. ([`src/server.c:325-328`](../../../src/server.c#L325-L328), [`src/server.c:367-397`](../../../src/server.c#L367-L397), [`src/db.c:1134-1141`](../../../src/db.c#L1134-L1141), [`src/flatstore.c:54-68`](../../../src/flatstore.c#L54-L68))

## Callers and related mechanisms

The versioned write entry point is `setKeyVersioned`. Direct atomic users include whole-value destination restore, logical-delete tombstone installation, `MSETNX` reservation, versioned `DEL`, and versioned `MSET`; each records the returned object with `csMsetRecordInstall`. ([`src/db.c:1569-1572`](../../../src/db.c#L1569-L1572), [`src/server.c:11282-11333`](../../../src/server.c#L11282-L11333), [`src/server.c:11477-11539`](../../../src/server.c#L11477-L11539), [`src/server.c:11542-11599`](../../../src/server.c#L11542-L11599))

The ordinary key-read entry point `lookupKeyReadWithFlags` sends a metadata-bearing head to `kvobjVersionAt`; write-side conflict checks also call the resolver with a `NULL` reader and the current committed frontier. ([`src/db.c:361-403`](../../../src/db.c#L361-L403), [`src/server.c:11477-11490`](../../../src/server.c#L11477-L11490))
