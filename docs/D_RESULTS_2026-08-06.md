## Step 3 — reorder (knob `tomokv-reorder` {0,1,2}, default 0)

Admission-time permutation of the current window before any ring slot is written (SPSC + ring
sizes untouched). Partition-by-worker (same-key order **structural**) → heads (never demoted) →
class C0–C3 with same-bucket grouping. Dependency guard = the routing xxh64 kept whole
(`tomo_key_h`); same-key collision fences the run's remainder to arrival order.

**Correctness (level 0 vs 2, single connection):**

    RPUSH 1..8000 → LRANGE monotonic OK    INCR ×8000 → exact    interleaved 2-key monotonic OK

`fences ≈ runs` on the single-key hammer proves the guard is what preserved order. Level 0 is
provably inert (0 engagement, no scratch write).

**Cost/benefit A/B (level 0 vs 2, interleaved ×3, io4ex4, full keyspace):**

    p32 SET −1.62%   p32 GET −0.78%   p32 MIX −1.63%   ZRANGE −1.11%

Consistent small cost (the O(r²) guard + scratch stage), **no benefit on any cell — as predicted**.
None of these is the verdict regime: p32MIX is 1:1 but both ops are cheap point ops, ZRANGE-alone
is all-C3 (SJF has nothing to sort), and this is a single-CCD box with no cross-node stall variance
for reordering to hide. The reorder's benefit is **tail latency under mixed command cost on
multi-CCD** — step 4 (`tail_mix`) + the EPYC box. Under the 3 % budget; ships OFF; correct by the
knob philosophy (semantically-active mechanism, gated, engagement-counted).
