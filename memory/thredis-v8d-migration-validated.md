THredis-opt-v8 **v8d online resharding is implemented and validated** (2026-06-20) per [[thredis-v4-tunable-apparatus]]'s plan and the RESHARD_DOUBLEWRITE_PROTOCOL.md effect-log design.

**What works (validated):** a single totally-ordered A→B effect log moves a contiguous bucket range from worker A (src) to adjacent worker B (dst) with no global pause.
- COPYING: A appends RDB-serialized post-image / tombstone after each commit (hooks in `workerExecFake` and `csSubExec`); B replays in order via `dbAdd`/`dbSyncDelete`; A's background `kvstoreScan` cold-copies. Validated **byte-exact** (an order-independent XOR checksum of RDB(value) per range key, src vs dst) under: cold copy, ~95k live single-key overwrites, cross-shard MSET overwrites, and deletes.
- Cutover: DRAINING → per-IO-producer drain-fence (each producer pushes ONE sentinel via `migPushFenceIfNeeded` in beforeSleep/beforeSleepIO + the dispatch hold) → wait applied≥S_final → FLIP table+`worker_bucket_end` → CLEANUP (worker A deletes the range) → DONE. ~ms under load, no hang, no crash. Post-cutover the range is served by B; old owner cleaned up; single-key AND cross-shard reads correct.
- Driven manually via `DEBUG RESHARD START <lo> <hi> <src> <dst>` / `CUTOVER` / `STATUS` / `FIND <key>` (needs `--enable-debug-command local`).

**Two cutover bugs found+fixed during validation:** (1) deadlock — must publish `fence_gen`/`fence_count` BEFORE `phase=DRAINING` (release) so a producer that observes DRAINING also sees the fence; (2) `nprod = my_io_threads` NOT +1 — main thread is IO-producer iotid 0, separate IO threads are iotid 1..my_io_threads-1 (server.c:9779 "Thread 0 is the main thread, start from 1"); worker queue slot `my_io_threads` exists but has no producer. Also `createFakeClient(parent)` derefs `parent->tid` — drain sentinel uses a zeroed static `mig_fence_parent`.

**EWMA auto-trigger DONE+validated (2026-06-20):** `reshardAutoTune()` runs 1Hz in serverCron (main thread, control-plane only — the routing hot path stays one bucket-table byte load, no load state on it). Per-shard EWMA of a new monotonic `worker->ops_total`; on `hottest > imbalance_pct/100 * mean` (and mean>min_ops) it shifts `chunk` boundary buckets to the cooler adjacent neighbour via a full-auto migration. Knobs: `thredis-reshard-auto` (default OFF), `-imbalance-pct` (150), `-min-ops` (20000), `-ewma-alpha-pct` (30), `-chunk-buckets` (64). Validated: 25 back-to-back auto-migrations under skewed load, all complete, byte-exact, no crash. (Single-hot-key load can't fully balance — the hotspot just gets chased neighbour-to-neighbour; realistic multi-key skew converges. Mechanism is sound.)

**Cutover drain-fence REWRITTEN to a hybrid (2026-06-20)** after two bugs surfaced under repeated auto-migrations: (1) `fence_gen` was reset to 0 in reshardArm so every migration got gen==1 and producers' thread-local dedup skipped pushing on migration #2+ — fixed by making `fence_gen` MONOTONIC (never reset). (2) idle producers blocked in epoll never push their sentinel. New fence: a producer slot is "drained" when EITHER worker A pops its drain sentinel (busy producer, sets `fence_acked[queue_idx]`) OR A's queue from that slot stays empty ~2ms (idle producer — nothing in flight). No cross-thread event-loop wake needed. `fence_count` replaced by `_Atomic fence_acked[MY_IO_THREADS_MAX+1]`.

**Ref-fence proven UNNECESSARY (not implemented):** the protocol's D4 zero-copy UAF assumed worker A is *retired* (fork/rebuild). In adjacent-shift A persists, so `workers[A].freeback[]` stays valid and a zerocopy reply's +1 refcount keeps the value alive until flush; `dbSyncDelete` in CLEANUP only drops the dict's ref. Validated under ASAN: 25 migrations + big-value (2KB) zerocopy reads on the migrating ranges → 0 UAF/heap-overflow/double-free; clean-shutdown leak check 0 leaks. `outstanding_a_refs` left as a 0 no-op.

**Both move directions validated:** suffix (B=A+1, `worker_bucket_end[src]=lo`) and prefix (B=A-1, `worker_bucket_end[dst]=hi`).

**Adversarial review (5-lens workflow) found 3 real bugs — ALL FIXED + re-validated (2026-06-20):**
1. CRITICAL cross-shard hold gap: `migHoldIfDraining` only checked `argv[1]`; a cross-shard MSET/DEL whose first key is out-of-range but a later key is IN range bypassed the cutover hold → late log entry past s_final → clobbered a post-flip B write. FIX: `migHoldKeyIfDraining` per-key in `dispatchCrossShard` for CS_MSET/CS_DEL.
2. HIGH lazy/active-expiry tombstone gap: `migCaptureEffect` only fires on CMD_WRITE, so a range key A expires (via a READ's lazy expiry or active-expire) wasn't logged → B resurrected it. FIX: `migCaptureImplicitDelete` in db.c `deleteExpiredKeyAndPropagate`+`deleteEvictedKeyAndPropagate`, STRICTLY gated to A's own shard (db==&workers[src].db[id]) so a tombstone never fires from the IO-side db.
3. CRITICAL teardown/re-arm race: `usleep(2000)` before migLogFree + `active=0` published BEFORE the free → B UAF on the freed log AND a new migration could overwrite migration.log → double-free. FIX: RCU-style — worker B heartbeat `loop_seq` + B drain gate `phase!=MIG_DONE`; coordinator waits B looped past DONE, frees log, then publishes `active=0` LAST (the one-at-a-time gate), closing both races. `fence_count`→per-slot `fence_acked[]`, `fence_gen` monotonic.

**Re-validation (all pass):** all-commands pre/post-migration test (`/tmp/v8d_cmdtest.py`) = 25/25 identical pre==post across strings/counters/bits/hashes/lists/sets/zsets/TTL/TYPE/GETDEL + cross-shard MGET/MSET/EXISTS, TTL key correctly NOT resurrected (fix #2). ASAN: 22 back-to-back auto-migrations + 2KB zerocopy reads = 0 UAF/double-free/leak (teardown fix). Verified xxh64 replica in `/tmp/v8d_keys.py` (bit-exact) for key placement without the bulk-FIND path.

**CORE-AWARE load balancing ADDED (2026-06-20, knob `thredis-reshard-core-aware` default ON):** each worker auto-calibrates its core speed at startup (fixed compute loop timed by WALL clock — invariant-TSC wouldn't show core speed) → `server.worker_capacity[]`. On this box: P-cores 0-3 cap ≈31.7k, E-cores 4-7 ≈24.9k (~27% faster). The EWMA balancer targets equal `load/capacity` (not equal ops), so faster/turbo/nearer-NUMA cores carry proportionally more. Validated: calibration separates P/E, 12 core-aware auto-migrations complete clean.

**BENCH findings (honest):** cross-shard fan-out — GET 424k ops/s; MGET×2 354k ops/s = 709k KEYS/s (fan-out yields more keys/s per round-trip). Hot-key LB efficacy: for LIGHTWEIGHT in-cache GETs the workload is NOT worker-bound — concentrating keys on one worker is actually FASTER (cache locality: 1.25M concentrated vs 1.07M spread), so LB doesn't help and can add overhead; **LB pays off only for worker-CPU-bound workloads (heavy per-op commands / large values), not cache-resident GET**. (Bench methodology caveat: memtier can't target one worker's hash-scattered keys, so the skew hammer is a pipelined Python multi-proc — treat ON as a lower bound.)

**Migration-rate control = CONVERGENCE DETECTION (no time cooldown, no permanent threshold raise — user rejected both).** `reshardAutoTune` keeps the BASE `thredis-reshard-imbalance-pct` threshold and migrates a hotspot only while it actually shrinks the peak load/capacity: records `mig_peak_pre`=peak before the migration, waits `mig_settle`=4 ticks for the EWMA to absorb the move (EWMA is NO LONGER reset post-migration, so the guard can measure), then if the new peak hasn't dropped >15% the hotspot is UNBALANCEABLE (single hot key just relocates) and it STOPS chasing. Balanceable many-key skew keeps shrinking each step → converges fully; a worse NEW imbalance resets via the balanced path and is handled immediately. Validated: unbalanceable single-key skew = 1 migration then stop (was 5-12 thrashing).

**3-WINDOW BENCH (the real picture, 2026-06-20):** server-side RPS = diff of `DEBUG RESHARD OPS` (sum of per-worker `ops_total`; the main `instantaneous_ops_per_sec` does NOT count worker-dispatched commands — reads ~0). One deterministic manual migration, 8 pipelined load procs, 5000×256B keys on w2: PRE 1,044k rps → DURING migration 1,049k (**+0.5%, NO drop**) → POST (keys split w2+w3) 1,009k (**−3.4%**). Takeaways: (1) the online migration is **non-disruptive** — cold-copy + cutover run concurrently at full RPS; the earlier "significant loss" was migration THRASHING, not the migration itself. (2) Post is slightly negative because lightweight cache-resident GET is NOT worker-bound (concentrated has better locality); LB only helps worker-CPU-bound workloads.

**WORKER-BOUND LB RESOLVED with a saturating C load gen (`harness/loadgen/cload.c`, 2026-06-20):** built a raw-socket pipelined multi-thread load gen with embedded bit-exact xxh64 to target one worker's keys (the Python gens were client-bound ~1.5M). Findings: (1) simple GET is **IO-dispatch-bound** — concentrated-on-1-worker GET caps ~1.1M with 2 IO threads regardless of command. (2) With **io-threads(5) > worker-threads(3)** the server is genuinely **worker-bound**: single-worker BITCOUNT-8KB caps ~116k. (3) BUT auto-LB did NOT raise throughput there (OFF 116k → ON 116k) — the adjacent-shift + convergence-stop policy UNDER-BALANCES a concentrated hot region: worker 1 shed to both neighbours but kept ~65% of the range ([1557,2442) stayed), the peak ping-ponged to a neighbour, and the convergence guard halted after ~5 migrations. So the LB mechanism is cheap+correct but its POLICY only helps gradual skew, not a concentrated hotspot. Next: test with YCSB/zipfian (realistic gradual skew), and/or a scatter redistribution policy + relaxed convergence for worker-bound load. Caveat: `instantaneous_ops_per_sec` reads ~0 (worker commands bypass it) — use `DEBUG RESHARD OPS`.

**DUAL CPU-PINNING MODES added (`thredis-pin-mode`, IMMUTABLE, default 0):** 0=manual (worker i→core i, reproducible — unchanged); 1=smart topology-aware — orders cores by shared-L3/CCD group (reads /sys cache levelN/id) so consecutive workers pack onto one CCD, + per-worker NUMA-local `set_mempolicy(MPOL_PREFERRED)` (raw syscall, no libnuma) so shard memory is node-local. EPYC/Threadripper-targeted, OFF for now (single-L3/NUMA box: smart==manual, plumbing validated). MIGRATION-AWARE by construction: `migApplyOne` runs on worker B's thread under B's NUMA policy, so migrated data is allocated node-local to its new owner automatically; adjacent workers (which swap buckets) co-locate on one CCD.

**TSAN validated (2026-06-20, build with `MALLOC=libc SANITIZER=thread` — jemalloc is INCOMPATIBLE with TSAN, default build fails):** ran the full migration lifecycle + cross-shard + bulk-inline under ThreadSanitizer. **ZERO races in any mig*/reshard* function — the v8d fences are race-clean.** 23 reported races are all pre-existing/benign: 17 on `global 'server'` (workers' relaxed reads of clock/stats — `updateCachedTimeWithUs`, etc.), the SPSC queue (`workerQueuePush` q->jobs[t]= — startup init-vs-use HB edge TSAN misses; correct via release/acquire on tail), and my cross-shard `csSubExec:5346 = server.dirty++` (benign stats counter, same pattern as all worker writes). The inline-pipeline `clients_pending_write` race did NOT surface under TSAN (timing-dependent; gdb root-cause stands).

**FIND crash ROOT-CAUSED — pre-existing, NOT FIND, NOT the data path:** any bulk-`--pipe` INLINE (non-worker-dispatched) command crashes (e.g. `DEBUG SET-ACTIVE-EXPIRE` too). gdb: `handleWorkerReplies`→`AddReplyFromClient`→`_prepareClientToWrite`→`putClientInPendingWriteQueue`→`listLinkNodeHead` on a wild head — a RACE on `server.clients_pending_write[iotid]` in the inline-fake reply drain across IO threads (len>0/bad-head at crash, len=0 after). Data commands are worker-dispatched (safe); only pipelined admin/inline commands hit it. FIND itself is now pure-functional (routing only; the unsafe cross-thread present_in scan was removed). A real but separate concurrency fix; deferred (don't bulk-pipe inline commands).

**Still open (smaller):** v8c unified int-knob refactor; root-cause the bulk-FIND crash; the EWMA "hotspot chasing" under pathological single-key load is a policy nicety, not a correctness issue.
